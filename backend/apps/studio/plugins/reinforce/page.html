SyMoNeuRaL Reinforce

A training bay, not a status panel. Pick a base model that is genuinely on this box, pick a predetermined tuning method, and see what the run will cost before it starts. The technique is 4-bit low-rank adaptation: the base weights are quantised to four bits and frozen, and only a small adapter is trained. That is what makes a 7B model trainable on one 15.92 GiB card at all — full fine-tuning of the same model would need roughly eight times this card.

Three things can be optimised here, and they are genuinely different: imitation of examples you provide, preference between two answers to the same prompt, and reinforcement, where the model writes its own answers and is scored on them. Only the last of those is reinforcement learning. All three run as low-rank adapters on the one card, all three are serialised against everything else on this box, and the same rule covers all three: every number below is labelled measured, vendor or projected, and the reinforcement figures are projected because no reinforcement run has finished here yet.

This surface is off. It accepts work only when the operator switches it on, because a training run takes the whole GPU and is never evicted to serve a page — an open one would take chat, image and remix offline for a single request.

4 · What a reinforcement run is scored against

The reinforcement method needs something to score its own output with. There is no learned reward model here — training one needs a second network beside the policy and this card does not have room for it. What runs instead is a small set of rules, and this is the honest description of what that buys and what it costs: a rising reward is evidence that a program's score went up. It is not by itself evidence that the model got better, and every one of these functions can in principle be satisfied by output that is worse. That is why completions are logged for a human to read, why no run here carries a quality claim, and why the reward table below states each function's weight.

5 · Start a run

Configure

There is no default dataset and no fallback. SyMoNeuRaL's own training corpus is a protected artefact: it is never listed, previewed, counted or read by this surface, and naming its path here is refused rather than accepted. Nothing this page returns — including an error message — contains a line of dataset content.

This run takes the whole rack

A fine-tune holds the GPU until it finishes or is stopped deliberately. Chat, image and remix queue behind it for its entire duration, and the governor will not evict a training run to serve a page view. That is architectural, not a limitation waiting to be engineered away — one card, and the weight sets do not co-fit.

What this objective reports

Progress, loss, reward and VRAM are read from the training process itself. The panel shows only output it recognises: anything else the process prints is discarded rather than displayed, because a training process's stdout can carry a line of the dataset in a traceback — and for the same reason a failure here reports an exception's class and the stage it happened in, never its message. The raw log stays on the box and has no URL, which is also why any series drawn above says how many steps it was drawn from: the panel is given a tail of that log, not the whole run.

What one 16 GiB card cannot do

Published for the same reason the PCIe Gen 3 ×8 ceiling and the failed multi-stream overlap are published: a negative result measured here is worth more than a positive one taken from somebody's marketing.

  • No full fine-tuning, of anything. Weights, gradients and two optimiser moments for a 7.6B model come to roughly 113 GiB — about eight times the budget. projected
  • No 14B at all — and this reverses an earlier estimate. A 14B was projected here as feasible at rank 16 and sequence 1024. Then a real run on the 7B measured its peak and found the projection 2.03 GiB light, because the parameters that are not quantised — the embeddings and the output head — are converted to full precision before training, at four bytes each rather than two. On a model with a 152,064-token vocabulary and an untied output head that is 1.56 billion parameters, or 5.8 GiB of the budget before a single activation exists. The corrected arithmetic puts every 14B configuration over the limit, so the preset table refuses all of them and shows the sum. measured on the 7B, projected onto the 14B.
  • Lowering the rank does not rescue a model that is too large. Rank governs the adapter, and the adapter is a fraction of a gibibyte of an eleven gibibyte problem. The only rungs that help are a shorter sequence and a smaller base, and the panel says which one it is offering. projected
  • No training while serving. One card, serialised. A run locks chat, image and remix out for its whole duration.
  • No multi-GPU anything, and CPU offload is not a rescue. One card, no NVLink, and this host is capped at PCIe Gen 3 ×8 — offloading optimiser state across that link every step converts a memory problem into a wall-clock one. measured
  • No learned reward model, and therefore no RLHF in the usual sense. Training a reward model means a second network of comparable size beside the policy, and then the policy optimisation needs both resident at once. On a card that is already near 12 GiB of a 14.2 GiB practical budget for the policy alone, there is no arrangement of the two that fits. What is offered instead is rules-based reinforcement: the scoring functions are written down, which makes them auditable and also makes them gameable in ways a learned model would not be. projected
  • No vLLM rollouts on this box, and llama.cpp is refused for them on correctness. vLLM's co-located mode wants a second copy of the weights plus a pre-allocated KV pool; there is no fraction of the card that leaves both alive, and vLLM is not installed here. Its server mode is supported and needs a machine that is not this one. llama.cpp is the interesting refusal: it is already built here and already fast, and it still cannot be a rollout engine, because it serves a quantised GGUF of the base model and cannot carry the adapter that is changing every step. Its completions and their log-probabilities would belong to a different model than the one taking the gradient — off-policy from step one, and silently. A fast generator that is not the policy is not a rollout engine; it is a different model's opinion.
  • Short completions, few of them. A reinforcement run generates n completions per prompt before it can take a single step, and every one of them costs a KV cache and a set of activations. That term multiplies, so the group size and the completion length — not the rank — are what decide whether a reinforcement configuration fits at all, and the profile that ships here is capped well below what a multi-card setup would use. projected
  • None of the reinforcement arithmetic has been measured yet. The supervised path has exactly one real peak behind it, and that measurement is what corrected the 14B projection by 2.03 GiB. The rollout and reference terms have no such run behind them: they are derived from the trainer's source with the lines cited, and they are labelled projected everywhere they appear. The first reinforcement run to finish will retire that projection for its own cell and no other. projected
  • A reward is not a quality measurement. The panel reports the reward a run's own scoring functions produced. That is a real reading of that score and nothing more — no claim is made here that a higher number is a better model, because establishing that needs a human reading the completions, and no such evaluation has been run on this box.
  • Nothing trained here is served automatically. A finished run produces adapter weights in the training format; the chat surface loads a different one. A page that said "trained" while chat still ran the previous adapter would be a dishonest status, so promotion stays a deliberate, manual step. A run started from an existing adapter does not write back to it either — the one it was given is opened read-only.

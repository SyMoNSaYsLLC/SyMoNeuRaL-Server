It exists because the original playbooks had drifted: they pointed at repository paths that no longer exist, told you to build a sample NVIDIA has since deleted, and quoted generic hardware numbers for a machine nobody owns.

The five findings that change how you should work on this box

  1. PCIe is your bottleneck, and it is worse than the spec sheet implies. The GPU can do Gen 5. The host caps it at Gen 3, 8 lanes. Measured host↔device throughput is ~6.9 GB/s up, ~7.2 GB/s down — about 1% of the GPU's internal memory bandwidth. Anything that streams data across PCIe is running on a drinking straw.
  2. Once data is resident, the GPU is fast. Measured 752 GB/s of real DRAM throughput (84% of the 896 GB/s theoretical peak), confirmed independently by three different samples. The design rule follows directly: get data onto the GPU once, keep it there.
  3. Stream-overlap tuning does nothing here — streamingCopyComputeOverlap measured 1.00x / 0.98x / 0.93x for 2 / 4 / 8 streams. Not a bug: transfer so dominates compute on a Gen 3 x8 link that there is nothing to hide it behind.
  4. Launch overhead is worth attacking. CUDA graphs gave 1.91x on a small-kernel loop, and shared-memory privatization gave 89.5x on histogram atomics. Both are bigger wins than any kernel micro-optimisation in the set.
  5. Keep python/.venv pristine; isolate every extra. Nine samples need packages beyond requirements.txt, and three more (matrixMulSharedMem, pageRank, processCheckpoint) carry pins that directly contradict the base stack. Worse, numba-cuda silently downgrades numpy 2.5.2 → 2.4.6 if you let it into the base environment. Everything extra belongs in its own venv outside the project tree — see Part II.

The PCIe ceiling — the most important thing on this page

The original Playbook 01 pasted this and moved on:

pcie.link.gen.current, pcie.link.width.current
1, 8

That reading is an idle power-saving state, not a hardware fact, and treating it as one is exactly the kind of error this document exists to remove. Here is the full picture from nvidia-smi -q:

GPU Link Info
    PCIe Generation
        Max            : 3      <- what this link will ever negotiate
        Current        : 1      <- idle downclock (ASPM)
        Device Current : 1
        Device Max     : 5      <- what the GPU is capable of
        Host Max       : 3      <- what the motherboard offers  <<< the real cap
    Link Width
        Max            : 16x
        Current        : 8x

Sampled every 0.4 s during a sustained transfer benchmark, the link trained up to Gen 3 and stopped — never Gen 4, never Gen 5, never wider than 8x:

idle under load
PCIe generation 1 3 (= Max, = Host Max)
Link width 8x 8x
Power draw ~12 W ~57 W
Temperature 44–45 °C 47–48 °C

Gen 3 x8 = 7.88 GB/s theoretical. Measured, with pinned memory:

Transfer Measured % of Gen 3 x8 peak
Host → Device (pinned) 6.94 GB/s 88%
Host → Device (pageable) 6.49 GB/s 82%
Device → Host (pinned) 7.20 GB/s 91%
Device → Host (pageable) 7.15 GB/s 91%

The link is running at essentially its full Gen 3 x8 capability. There is no tuning fix — it is the slot. What you can do is stop crossing it: keep working sets resident in the 15.9 GiB of VRAM.

(If this is unexpected, it is worth checking whether the card is in the CPU-direct x16 slot rather than a chipset slot. Host Max: 3 suggests the platform itself tops out at Gen 3, but slot choice is the first thing to rule out.)

The L2 trap

The same benchmark at different sizes:

Buffer D2D reported What is really happening
8 MB 994 GB/s fits entirely in the 48 MB L2 — not a DRAM measurement
32 MB 493 GB/s partially cached
128 MB 380 GB/s DRAM-bound
512 MB 380 GB/s DRAM-bound, stable

With 48 MB of L2 on this part, any bandwidth test under ~100 MB is measuring cache. This is the single easiest way to publish a wrong number.

A driver quirk worth knowing

Driver 610 reports stale clocks: clocks.sm read 480 MHz while utilization was 100%, and several clock queries return Requested functionality has been deprecated. Maximum clocks are reported correctly (3,210 MHz SM / 14,001 MHz memory). Do not trust nvidia-smi instantaneous clock readings on this driver — use power draw and achieved throughput as your activity signal instead.

Reading

A 26.9 B model runs fully GPU-resident on a 15.92 GiB card. The engine needed no work: the GGUF header declares general.architecture = qwen35 and the local llama.cpp build already carries LLM_ARCH_QWEN35.

This validates the bandwidth formula, with a correction. 752 GB/s ÷ 11.85 GB predicts 63.46 tok/s; the card delivered 56.90. The formula is ~11.5% optimistic — real decode came in at 90% of predicted. That is one datapoint, not a calibration curve, but it is the first time any row of the table above has had a measurement to sit next to. Treat the other predicted rows as similarly optimistic rather than as results.

Measured: what context fits in the headroom

The 11,916 MiB bench figure is peak at llama-bench’s short context and implies more headroom than a real session has. Every number below is total resident VRAM reported by nvidia-smi with llama-server loaded and idle at that context, same weights, -ngl 99:

Context KV type Result Resident VRAM
8,192 f16 loads 12,354 MiB
16,384 f16 loads 12,874 MiB
32,768 f16 loads 13,914 MiB
32,768 q8_0 loads 13,040 MiB
65,536 q8_0 loads 14,288 MiB
131,072 q8_0 fails —

The 128K failure is a real allocator error, not a timeout:

ggml_backend_cuda_buffer_type_alloc_buffer: allocating 598.50 MiB on device 0:
    cudaMalloc failed: out of memory
llama_init_from_model: failed to initialize the context:
    failed to allocate buffer for rs cache

Note what failed: the recurrent-state cache, not the KV cache. This architecture is hybrid, and recurrent state is sized per slot rather than per token, so do not read the 128K failure as a point on the KV slope below.

KV grows linearly, and the slope is what the rows above actually measure. Taking differences rather than absolutes (the absolute figures include the weights and the compute buffers, so only the deltas isolate KV):

  • f16: 63.5 MiB per 1K tokens — 16K→32K costs 1,040 MiB for 16,384 tokens.
  • q8_0: 38.1 MiB per 1K tokens — 32K→64K costs 1,248 MiB for 32,768 tokens.

So q8_0 is about 60% the cost of f16 here, not the half you would get from the bit width alone. At the same 32K context the two differ by a directly measured 874 MiB (13,914 vs 13,040), and that saving is what buys the jump from 32K to 64K.

64K at q8_0 is the largest context that loads, at 14,288 MiB of 16,303 — about 2 GB of the card still free.

What this does not establish, in order of how likely it is to mislead. It is a load-and-idle measurement: the server allocated the context and sat there, and nothing here exercises it under generation. Concurrency is untested and matters — that context is a pool shared across the server’s slots, not 64K guaranteed to each simultaneous user. Whether q8_0 KV degrades output quality is not measured, only that it allocates. And the smaller quants of this model (UD-IQ2_M at 10.85 GB, UD-IQ2_XXS at 9.39 GB) have not been loaded here; they are smaller on disk, which is a file size, not a fit.

The environments

Policy: $CUDA_SAMPLES/python/.venv stays pristine. It holds exactly the four packages in python/requirements.txt and nothing else. Every sample that needs anything beyond that gets an isolated venv outside the project tree.

This is not fussiness. Two of the extras actively damage the base environment: numba-cuda pins numpy<2.5 and will silently downgrade your numpy, and the three pinned samples below contradict the base cuda-core/cuda-python versions outright. Keeping them separate means the environment you rely on never moves.

$VENVS/venv-extras 9 samples adds cuda-cccl, nvtx, numba-cuda, torch, mpi4py — numba-cuda would downgrade base numpy 2.5.2 → 2.4.6

Playbook 01 — Hardware & the Math of Inference

Why models run at the speed they do, and how to size a model to silicon before downloading a single byte

Most people benchmark by trial and error. You're going to learn the three formulas that predict performance before you touch the hardware. This is the highest-leverage knowledge in the whole manual.

Stage 1 — The three numbers that rule everything (30 min, pen and paper)

Every piece of hardware has: 1. Memory capacity (GB) — determines what fits 2. Memory bandwidth (GB/s) — determines decode speed 3. Compute (TFLOPS) — determines prefill speed and batch throughput

Formula 1: Does it fit?

Model VRAM ≈ params × bytes_per_param + KV cache + overhead (~1-2 GB)

FP16: 2 bytes/param    INT8: 1    Q4: ~0.55    IQ2: ~0.3

Example: 8B model at Q4 ≈ 8 × 0.55 = 4.4 GB + KV + overhead → fits in 8 GB.

Formula 2: How fast will it generate? (the big one)

Token generation is memory-bandwidth bound: every token requires reading ALL weights from memory once.

Max tokens/sec ≈ memory_bandwidth (GB/s) ÷ model_size_in_memory (GB)

Examples: | Hardware | Bandwidth | 8B @ Q4 (4.4 GB) | 70B @ Q4 (~38 GB) | |---|---|---|---| | RTX 4090 | ~1000 GB/s | ~220 tok/s | doesn't fit | | RTX 3060 12GB | ~360 GB/s | ~80 tok/s | doesn't fit | | Apple M4 Max | ~546 GB/s | ~120 tok/s | ~14 tok/s | | DDR5 desktop (2ch) | ~90 GB/s | ~20 tok/s | ~2.4 tok/s | | Raspberry Pi 5 | ~17 GB/s | ~4 tok/s (1B model: ~30) | no |

This one formula explains: why quantization speeds up decoding (smaller model = fewer bytes to read), why CPUs with fast RAM are viable, why a 4090 barely beats a 3090 at single-stream decode (similar bandwidth), and why Macs are good at this (unified memory bandwidth).

Formula 3: Prefill (prompt processing) is compute-bound

Prefill tok/s ≈ compute_TFLOPS × efficiency / (2 × params)

Long prompts stress compute; generation stresses bandwidth. Two different bottlenecks — a machine can be great at one and bad at the other.

Playbook 02 — Transformer Anatomy & Profiling

Open the hood: what's inside a model, where the bytes live, and how to measure where time goes

Stage 1 — Dissect a real model (1 hour)

def param_census(model):
    buckets = {}
    for name, p in model.named_parameters():
        key = ("embed" if "embed" in name else
               "attn"  if any(k in name for k in ["q_proj","k_proj","v_proj","o_proj"]) else
               "ffn"   if any(k in name for k in ["gate_proj","up_proj","down_proj"]) else
               "norm"  if "norm" in name else "head")
        buckets[key] = buckets.get(key, 0) + p.numel()
    total = sum(buckets.values())
    for k, v in sorted(buckets.items(), key=lambda x: -x[1]):
        print(f"{k:8s} {v/1e6:8.1f}M  {100*v/total:5.1f}%")

param_census(model)

What you'll find (roughly, for modern LLMs): - FFN ≈ 55-65% of parameters — the biggest target for pruning/quantization - Attention ≈ 20-30% - Embeddings ≈ 5-20% (huge share in small models — why small models resist compression more) - Norms ≈ rounding error

Also decode the config: num_key_value_heads < num_attention_heads means GQA (grouped-query attention) — fewer KV heads = smaller KV cache = cheaper long context. This single config line predicts long-context memory cost.

Stage 2 — KV cache math (30 min, calculator)

The forgotten memory consumer. Per token cached:

KV bytes/token = 2 (K and V) × num_layers × num_kv_heads × head_dim × bytes_per_value

Example, Llama-3.1-8B (32 layers, 8 KV heads, head_dim 128, FP16):

2 × 32 × 8 × 128 × 2 = 131 KB/token  →  128K context ≈ 16.8 GB (!)

The KV cache of one long conversation can exceed the model itself. This is why Playbook 06 exists.

Stage 4 — What each part does (the mental model to keep)

  • Embedding: token ID → vector. Lookup table, bandwidth-trivial.
  • Attention (QKV + output proj): mixes information across positions. The only place tokens talk to each other. Grows with context (via KV cache reads).
  • FFN (gate/up/down): per-token computation, where most "knowledge" is stored. No cross-token interaction. Biggest, most prunable, most quantizable.
  • Residual stream: the shared bus every layer reads/writes. Why you can delete layers and the model degrades gracefully instead of dying.
  • LM head: final projection to vocabulary. Often tied to embeddings in small models.

Practical consequences you now understand mechanically: | Observation | Cause | |---|---| | Long chats slow down and eat VRAM | KV cache growth, attention reads it every token | | MoE models are fast for their size | Only some FFN experts read per token → fewer bytes/token | | Quantizing FFN hurts least, embeddings hurt most | Knowledge is redundant in FFN; embeddings are lookup-precise | | Pruning targets FFN channels & whole layers | 60% of params, graceful residual-stream degradation |

Iron laws

  1. FFN is where the parameters are; attention is where the interaction is; KV is where the context cost is.
  2. KV cache is a first-class memory consumer — budget it like model weights.
  3. Profile before optimizing; the bottleneck is usually not where you guessed.
  4. Config file → performance prediction. Learn to read configs like spec sheets.

  1. The spec and the filters are the product; generation is the easy part.
  2. Verify executably whenever the domain allows it — a compiler is the cheapest, most honest judge.
  3. Never let the teacher grade its own homework (different judge model).

Stage 3 — Prompt caching: stop paying for the same prefix twice

Agents and RAG resend a giant, mostly-identical prompt every turn. Caching the prefix's KV skips recomputation:

  • llama.cpp server: caches the common prefix across requests automatically per slot; design prompts so stable parts (system, tools, documents) come FIRST and variable parts (user turn) LAST. Reordering a prompt can cut time-to-first-token 5-10x in agent loops.
  • vLLM: enable prefix caching:
vllm serve <model> --enable-prefix-caching

Then measure: send 20 requests sharing a 3K-token system prompt, compare TTFT with and without.

Prompt-structure rule that follows: immutable → semi-stable → volatile, top to bottom. Never put a timestamp at the top of a cached prompt (it invalidates everything below it).

Stage 4 — When context runs out anyway: the honest toolbox

  1. Summarize-and-roll: at ~70% full, summarize the oldest exchanges into a compact note, keep recent turns verbatim. Simple, effective, lossy — the standard for long chats.

  3. Context-window extension caution: models advertise 128K+ but quality at depth varies. Run your own "needle" test — plant 5 facts at different depths in a long document, ask for them, score recall by depth. Trust your table, not the marketing number.
  4. Sliding window / attention sinks: some models/runtimes keep only recent KV + a few anchor tokens. Good for streams; forgets the middle by design.

Playbook 07 — Speed Tricks: Speculative Decoding & Friends

2-4x more tokens/sec from the same silicon, and knowing which trick applies when

Playbook 01 taught you decode speed = bandwidth ÷ model bytes. That's the wall. This lab is about the legal ways around the wall: guessing tokens cheaply and verifying them in bulk, plus the smaller wins that stack.

Stage 0 — Why speculation works (5 min)

Reading all weights once produces ONE token — but verifying N candidate tokens in a single forward pass costs barely more than producing one (the weight-read is shared). So: let a tiny "draft" model guess 4-8 tokens, then have the big model verify them all at once. Accepted tokens are FREE bandwidth-wise. Output is mathematically identical to the big model alone — rejected guesses are simply discarded and regenerated.

Speedup ≈ acceptance_rate × draft_length, minus overhead. Predictable text (code, JSON, formulaic prose) accepts more → speeds up more.

Stage 2 — Chunking: where RAG is won or lost (1 evening)

Documents must be split before embedding. The trade: small chunks = precise retrieval but shattered context; big chunks = context intact but diluted embeddings.

# Solid default: 300-800 token chunks, 10-15% overlap, split on structure first
def chunk(text, target=500, overlap=60):
    import re
    paras = re.split(r"\n\s*\n", text)          # respect paragraph boundaries
    chunks, cur = [], ""
    for p in paras:
        if len((cur + p).split()) > target and cur:
            chunks.append(cur.strip())
            cur = " ".join(cur.split()[-overlap:]) + "\n" + p   # overlap tail
        else:
            cur += "\n\n" + p
    if cur.strip(): chunks.append(cur.strip())
    return chunks

Upgrades that matter, in order of value: 1. Prepend context to every chunk: "[{doc_title} > {section}] {chunk}" — cheap, big retrieval gains 2. Respect structure: never split mid-code-block or mid-table; markdown headers are gold 3. Semantic chunking (split at embedding-similarity dips) — marginal gains, try last

# Gold set: 20-30 (question, ids_of_chunks_that_answer_it) pairs from YOUR corpus
def recall_at_k(gold, k=5):

def run_bash(command):
    # SANDBOX: allowlist, no writes. Never hand a raw shell to a model.
    if any(t in command for t in [">", "rm ", "sudo", "mv ", "curl", "wget"]):
        return "DENIED: read-only tool."
    r = subprocess.run(command, shell=True, capture_output=True, text=True, timeout=15)
    return (r.stdout + r.stderr)[:4000]           # ALWAYS truncate tool output

def agent(task, max_steps=8):
    msgs = [{"role": "system", "content":
             "You solve tasks using tools. Think briefly, act, observe, repeat. "
             "When done, answer with FINAL: <answer>."},
            {"role": "user", "content": task}]
    for step in range(max_steps):
        r = client.chat.completions.create(model="local", messages=msgs,
                                           tools=TOOLS, temperature=0.2)
        m = r.choices[0].message
        if m.tool_calls:
            msgs.append(m)
            for tc in m.tool_calls:
                out = run_bash(**json.loads(tc.function.arguments))
                msgs.append({"role": "tool", "tool_call_id": tc.id, "content": out})
        else:
            return m.content
    return "STOPPED: step budget exhausted."

Stage 2 — Reliability engineering (what separates demos from tools)

  • Verify claims against ground truth. Models report success that didn't happen. After any state-changing action, CHECK: file exists? tests pass? exit code 0? Treat completion as a hypothesis to verify, not a fact to log.
  • Retries with feedback: on malformed/failed calls, append the error and let it try again (2-3 max), then fail loudly.
  • Structured scratchpad: for tasks > ~5 steps, have the agent maintain a STATE.md/plan it re-reads each step — context is not memory; the file is the memory.
  • Idempotent tools: design tools so running twice is safe; agents WILL run things twice.
  • Observability: log every step (prompt, call, result) as JSONL. Debugging agents without transcripts is archaeology without a shovel.

Deliverable: add verification + retry + JSONL logging to Stage 1's loop; show one transcript where verification caught a false success.

Stage 4 — Multi-worker orchestration (careful, here be dragons)

Patterns that work locally, in ascending complexity: 1. Pipeline: fixed stages (extract → transform → verify), each possibly a different model/specialist. Most reliable; start here. 2. Orchestrator-workers: a planner decomposes, workers execute in parallel, planner integrates. Use when subtasks are independent. 3. Reviewer pattern: generator + a separate verifier model that must approve (different model to avoid self-agreement bias — same principle as P05's judge).

Hard-won rules for multi-worker systems: - Single owner per resource. Two agents writing one file/repo = corruption. Route all writes through one worker; respect the routing protocol even when a shortcut looks faster — raise exceptions with the owner explicitly rather than working around it. - Handoffs are documents, not vibes: a handoff = task, context, acceptance criteria, and current verified state. (Your consolidation-script instinct is exactly right — formalize it.) - Shared state lives on disk (files, sqlite), never in "the conversation." - Parallelism multiplies throughput AND failure modes; add workers only after the single-agent loop is boringly reliable.

Deliverable: a 2-worker pipeline (e.g., small-model extractor → specialist formatter → verifier) with document handoffs, run on a real task from your own projects.

Iron laws

  1. An agent is a loop plus discipline: budget, truncation, verification, logs.
  2. Malformed output is the #1 small-model failure — constrain with grammars.
  3. Completion claims are hypotheses; disk state is truth.
  4. Route by difficulty: most steps are small-model steps.
  5. One writer per resource; handoffs as documents; state on disk.
  6. Multi-agent is an optimization of a working single agent, never a substitute for one.

Unified Memory (Managed Memory)

This sample uses ManagedMemoryResource for simplicity: a single allocation is accessible from both CPU and GPU without explicit transfers. For performance-critical workloads, consider LegacyPinnedMemoryResource + DeviceMemoryResource instead, which gives explicit control over host/device placement and transfer costs.

Unified memory is accessible from both CPU and GPU without explicit data transfers:

# Allocate unified memory
options = ManagedMemoryResourceOptions(preferred_location=device.device_id)
mr = ManagedMemoryResource(options)
src_buf = mr.allocate(n_bytes, stream)
dst_buf = mr.allocate(n_bytes, stream)
try:
    # Synchronize to ensure allocations are complete before CPU access
    stream.sync()

    # Create numpy views of unified memory using DLPack protocol (zero-copy)
    src_np = np.from_dlpack(src_buf).view(np.float32).reshape(H, W)
    dst_np = np.from_dlpack(dst_buf).view(np.float32).reshape(H, W)

    # CPU writes directly to unified memory
    src_np[:] = input_data

    # Launch kernel - buffers can be passed directly as arguments
    launch(stream, config, kernel, src_buf, dst_buf, H, W)
    stream.sync()

    # Return zero-copy view; caller must close buffers when done
    return dst_np, src_buf, dst_buf
except Exception:
    src_buf.close()
    dst_buf.close()
    raise

When returning a zero-copy view, the caller must close the buffers after use (e.g., in a try/finally block) to avoid leaking managed memory.

greenContext (Python)

Description

This sample demonstrates how to use green contexts with cuda.core to statically partition a GPU's streaming multiprocessors (SMs) so that independent kernels can run on dedicated subsets of the device.

This examples takes A long-running kernel that fills the GPU's SMs, and a short but latency-sensitive "critical" kernel is launched shortly after. Without green contexts, the critical kernel must wait for SMs to free up. With green contexts, the GPU's SMs are partitioned so the critical kernel has its own dedicated SMs and can start immediately.

Three timed scenarios are compared:

  1. Reference: the critical kernel alone on the primary context, with no competing work. Establishes the pure compute time of the critical kernel when every SM on the device is available to it.
  2. Baseline: both kernels run on the device's primary context, on two non-blocking streams that contend for all SMs.
  3. Green contexts: the SMs are split into two disjoint groups (e.g. 112 + 16). Each kernel runs on a stream that belongs to its own green context, so the critical kernel never waits for SMs held by the long-running kernel.

The headline metric is the total wall time of the critical kernel from launch to completion. In the baseline it is dominated by time spent waiting behind the long-running kernel. With green contexts it reflects the kernel's own compute time on its (smaller) SM partition. The reference row lets you separate those two effects:

  • baseline - reference is roughly the time the critical kernel spent waiting for SMs in the baseline run (the cost that green contexts eliminate).
  • green / reference is the compute slowdown caused by running on a smaller SM partition (the cost that green contexts introduce).

Sample: Memory Resources and Buffers (Python)

Description

This sample demonstrates the cuda.core memory management model: a MemoryResource owns a pool of memory and hands out Buffer objects that can be passed to kernels, copied between resources with Buffer.copy_to(), and viewed as NumPy or CuPy arrays through DLPack. The script exercises three common resources side-by-side:

  1. DeviceMemoryResource - device-local GPU memory. Every Device exposes a default pool via Device.memory_resource, and applications can create additional pools explicitly.

Reduction Tree Pattern

Parallel reduction uses a tree-based approach where each iteration halves active elements:

Initial:  [a0, a1, a2, a3, a4, a5, a6, a7]
Step 1:   [a0+a4, a1+a5, a2+a6, a3+a7]      threads 0-3 active
Step 2:   [a0+a2+a4+a6, a1+a3+a5+a7]        threads 0-1 active
Step 3:   [sum of all]                       thread 0 only

This requires only log2(N) steps to reduce N elements.

Avoiding Warp Divergence
// Good: Sequential thread IDs (warps stay coherent)
if (tid < s) {
    sdata[tid] += sdata[tid + s];
}

// Bad: Strided IDs (causes warp divergence)
if (tid % (2 * s) == 0) {  // Don't do this!
    sdata[tid] += sdata[tid + s];
}

processCheckpoint (Python)

Description

This sample demonstrates how to use the CUDA process checkpoint API via cuda.core.checkpoint.Process to suspend, capture, and restore the CUDA state of a running Linux process.

CUDA process checkpointing is the driver-level primitive that powers CRIU + cuda-checkpoint integration.

The sample:

  1. Allocates a GPU buffer and fills it with a deterministic pattern via a small kernel.
  2. Reads the buffer back to host and computes a SHA-256 hash.
  3. Runs the full checkpoint lifecycle on its own process: lock → checkpoint → restore → unlock.
  4. Reads the buffer back again and verifies that the hash is unchanged, proving that GPU memory contents survived the round trip.

The sample prints the CUDA process state after each step so the full state machine is visible:

         lock()          checkpoint()              restore()         unlock()
running ---------> locked ------------> checkpointed -----------> locked ---------> running
What You'll Learn
  • Creating a cuda.core.checkpoint.Process for the current process by PID and observing its .state transitions.
  • Running the full lock → checkpoint → restore → unlock cycle with a lock timeout.
  • The fact that restore() leaves the process in the locked state; you must still call unlock() to return to running.
  • Verifying that GPU memory is preserved across the checkpoint round-trip by comparing SHA-256 hashes of the buffer before and after.
  • The rough cost of each step (checkpoint and restore dominate and scale with the device-memory footprint being captured).

Key APIs
From cuda.core.checkpoint
  • checkpoint.Process(pid) - create a handle to a CUDA process by PID. Accepts os.getpid() for the self-checkpoint case shown here.

Benefits
  • No explicit transfers: Simplifies code by eliminating cudaMemcpy calls

  • Slower access: Limited by PCIe bandwidth vs. device memory bandwidth
  • Not for compute-intensive: Device memory is much faster for frequently accessed data
  • Discrete GPU overhead: Each access crosses PCIe bus
Best Use Cases
  1. Small data sets where transfer overhead dominates
  2. Data accessed infrequently by GPU
  3. Integrated GPU platforms (shared memory)
  4. Streaming data from host to device

ipcMemoryPool (Python)

Description

This sample demonstrates how to share GPU memory between Python processes using CUDA Inter-Process Communication (IPC) and cuda.core's IPC-enabled memory pools.

By default each process has its own CUDA virtual address space and cannot see allocations made by another process. With an IPC-enabled DeviceMemoryResource the parent allocates once, and the child process maps that same physical GPU memory into its own address space so both read and write the same bytes. The sample performs a round-trip test:

  1. Parent creates an IPC-enabled DeviceMemoryResource and allocates a Buffer.
  2. Parent fills the buffer with a known pattern.
  3. Parent sends the Buffer to a child process through an multiprocessing.Queue. cuda.core's pickle reducers re-create the memory resource and map the buffer in the child.
  4. Child verifies the parent's pattern, writes a new pattern, and signals completion.
  5. Parent verifies the child's writes.

Peer-to-Peer (P2P): When to Use
Benefits
  • Direct GPU-to-GPU transfers: Bypass host memory for faster communication
  • Higher bandwidth: PCIe or NVLink bandwidth between GPUs (up to 600 GB/s with NVLink)
  • Lower latency: No CPU involvement in data transfers
  • Efficient multi-GPU: Essential for scaling deep learning, HPC, and simulation workloads
  • Simplified programming: Kernels can directly access remote GPU memory
Requirements
  • Two or more GPUs: System must have multiple CUDA-capable GPUs
  • P2P support: GPUs must be P2P-capable (check with can_access_peer())
  • PCIe topology: Usually requires GPUs on same PCIe root complex
  • Platform support: Not available on Mac OSX, limited on ARM platforms
Best Use Cases
  1. Multi-GPU deep learning training (model parallelism, data parallelism)
  2. Large-scale scientific simulations across multiple GPUs

Available Functions
Result Verification

verify_array_result(result, expected, rtol=1e-5, atol=1e-8, verbose=True)

Verify computed results match expected values. The helper detects whether both arguments are NumPy arrays or both are CuPy arrays and uses the matching library's allclose (no unnecessary cross-device transfers).

Parameters: - result: NumPy or CuPy array with computed results - expected: NumPy or CuPy array with expected values (same kind as result) - rtol: Relative tolerance (default: 1e-5) - atol: Absolute tolerance (default: 1e-8) - verbose: Print test result (default: True)

Returns: - True if results match within tolerance, False otherwise

Example:

expected = a + b
if verify_array_result(c, expected):
    print("Computation correct!")
Package Check

check_cuda_requirements()

Check if required CUDA packages are available.

Returns: - True if requirements are met, False otherwise

Example:

if not check_cuda_requirements():
    sys.exit(1)
Design Philosophy

These utilities focus on common operations that are not part of cuda.core API: - Result verification for NumPy or CuPy arrays - Package requirements checking

For CUDA operations like device initialization, kernel compilation, and grid size calculations, samples should use cuda.core API directly to demonstrate the proper usage patterns.

    How this works, and what it is not

    One output, two surfaces. OBS’s recording output is configured as HLS: a playlist plus a run of two-second segments, written into this box’s backend/output/live/. While OBS is writing, that playlist is the live stream. When OBS stops cleanly, ffmpeg appends an #EXT-X-ENDLIST tag and the identical files become the recording. Nothing is copied, converted or re-encoded to produce the second one.

    Three states, not two. A playlist with that end tag is finished. A playlist without it that was written to seconds ago is live. A playlist without it that has not been touched in a long time is neither — it is what OBS leaves behind when it crashes, and it is listed as ended without a trailer rather than being shown as a stream that is still running. Treating “no end tag” as “live” would light the lamp above permanently after any crash, which would make it decoration.

    The readings and the video are independent. Scene, dropped frames and encoder output come from a websocket connection this server makes to OBS on loopback — it holds the password, the browser never sees it, and no router port is open for it. The video comes from reading a directory and needs no credential at all. So a closed OBS or a wrong password costs this page its readings and not its picture, and the two halves are separate modules that do not import each other so that stays true.

    What it is not. There is no transcode ladder. You get the one bitrate the encoder is producing, so a slow connection buffers rather than dropping to a lower quality — that is the honest cost of having no media server in the path, and it is the trade this page is making on purpose.

    Live surface

    The stream, off the box that makes it.

    OBS encodes on the RTX 5070 Ti described on the home page and writes HLS straight to this machine’s disk. There is no media server in between and no re-encode: what you are watching is the file the encoder is still writing. When the stream ends, that same file is the recording.
